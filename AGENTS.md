# Instructions for coding agents

This file is for AI coding agents working in JibunKit or in a host repository derived from it. People should start with the [README](README.md).

## Which repository this is

Run `git remote -v`.

- If `origin` is `y-aplus/JibunKit`, you are changing JibunKit itself. Follow [CONTRIBUTING](CONTRIBUTING.md); every file below is yours to change.
- Otherwise this is a **derived host**: a repository that merges JibunKit from a remote usually named `upstream` ([updating](docs/updating.md)). The rest of this file applies, and the owner's own rules are in `docs-local/AGENTS.md` when that file exists. Read it after this one; where they disagree, it wins.

Do not edit this file in a derived host. It comes from upstream and is replaced on the next merge; put local rules in `docs-local/AGENTS.md`.

## What to read

1. [Adding a feature](docs/mini-apps.md), before writing or moving a Feature.
2. The guide in [docs/guides](docs/guides/) for each system surface the Feature uses, such as location, notifications, widgets, camera or background work.
3. [Build requirements](docs/guides/feature-build-requirements.md), before adding Info.plist keys, usage descriptions or entitlements.

## What a derived host may change

A Feature lives in `Modules/<Name>/` with a `JibunKitFeature.json`. Adding or changing one touches only:

- `Modules/<Name>/`;
- `Tuist/ProjectDescriptionHelpers/ModuleFeatures.swift`, which `python3 Tools/jibunkit-feature.py sync` writes; do not edit it by hand;
- `JibunKitImports.json`, which the `add`, `update` and `remove` commands write;
- `Tuist/ProjectDescriptionHelpers/EnabledFeatureBuildRequirements.swift`, only to state a value the owner agreed on when two Features ask for different ones, or to turn on an optional extension;
- `docs-local/`, for the owner's notes.

Everything else comes from upstream: `Sources/`, `Tools/`, the rest of `Tuist/`, `.github/workflows/`, `docs/`, `UITests/`, `Tests/`, `Project.swift`, `Package.swift`, `Package.resolved` and the files at the repository root. Do not change them unless the owner asks for that change. A change there conflicts with the next upstream merge.

## When upstream code is wrong

If a tool, workflow, Core API or document from upstream fails or contradicts itself:

1. Do not fix it in the derived host.
2. Stop and tell the owner what failed, how to reproduce it, and the commit it was seen at (`git log -1 --format=%H upstream/main` or the merge base).
3. Offer to write an issue for upstream with those facts. Open it only when the owner agrees.
4. If the work must continue, use a workaround that leaves upstream files unchanged, such as calling a tool's function directly or running the steps by hand, and say that it is a workaround.

The owner may still decide to patch upstream code locally; then keep the patch in its own commit so it can be dropped when upstream fixes it.

## Checks after changing a Feature

```bash
python3 Tools/jibunkit-feature.py sync --check
python3 Tools/jibunkit-feature.py check Modules/<Name>
```

- `sync --check` fails when the connection is out of date: run `sync` and commit `ModuleFeatures.swift` with the Feature.
- `check` reports code that changes other Features' state, with the guide to follow.
- A usage description or entitlement that differs from another Feature's stops the build until the host states the agreed value in `infoPlistResolutions`, `localizedInfoPlistResolutions` or `entitlementResolutions` of `EnabledFeatureBuildRequirements.swift` ([build requirements](docs/guides/feature-build-requirements.md)). Look for the same key in other `Modules/*/JibunKitFeature.json` before adding one, and ask the owner for the shared wording.
- CI builds Feature packages for macOS. Keep iOS-only code in files wrapped in `#if os(iOS)` ([why](docs/mini-apps.md#your-package-is-also-built-for-macos)), and run `swift test --package-path Modules/<Name>` where Swift is available.
- `python3 Tools/compile-check.py` compiles the working tree for iOS on GitHub without a commit and prints compiler errors. It pushes a temporary branch to `origin`, so ask before running it if the owner has not said to.

Report what you ran and what you could not run. A compile is not a test on a device.
