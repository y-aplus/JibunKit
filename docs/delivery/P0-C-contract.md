# P0-C 追加・更新と0.7.0候補の契約

2026-09-12。P0-Aはmain `73fe9de`へ検証して統合。P0-B候補`5cffdf2`は通常CI中。本書は次の境界の準備であり、P0-Cの実装・検証完了を表さない。
対象は[plan.json](plan.json)のP0-4とP0全体。依存するP0-Bを確定してから候補SHAを固定する。

## 実装範囲

- TuistのFeature雛形とSwift Packageを維持する。通常の追加手順から、Package path、library product、host target依存、Integrationの公開定義、Registry登録、必要なビルド要求まで辿れるようにする。
- 欠けたpath/product/target依存とRegistry登録漏れを、失敗箇所と直すファイルが分かる診断へつなぐ。Swiftソースの正規表現検索だけで依存や登録を保証しない。Tuist/Swiftの生成・型検査と、生成hostで期待するFeature IDの存在を確認する試験を使い分ける。
- 異値のplist/entitlement等の拒否は既存FeatureBuildRequirementsのnative検査を再利用する。二つの要求の所有者、異値、解消先を示す既存診断を通常手順へ接続し、同じ機構を再実装しない。
- 独立FeatureのCore非依存性を保つ。寿命、保存予約、復元、削除、同意はIntegrationから必要な範囲を接続する。バックグラウンド処理もデータもない単純画面にダミーproviderを必須にしない。
- 更新例は二Packageの同名リソース/翻訳を保持したままAだけ更新する。ID・保存先を維持した追加フィールド等の互換更新と、壊れた更新を検証で拒否して直す手順を含める。既存resource比較とRecordsの移行を利用し、巨大な架空アプリは作らない。

## 初回CI前に揃える検証

| 条件 | 操作・観測 |
| --- | --- |
| P0-4.diagnostics | 意図的なpath/product/target依存/Registry漏れをそれぞれ作る。修正前の失敗理由と修正後の通過を記録。異値ビルド要求も既存native検査で拒否を確認 |
| P0-4.onboarding | READMEから手順だけで雛形を作成し単独・hostで開く。A更新後もA/BのPackageリソースと保存値が一致することを確認。生成処理の成功だけをUI成功と扱わない |
| P0-4.docs | 追加、寿命/保存の接続、同意/削除、更新、衝突解消、失敗からの復旧をREADMEから辿れる。現在状態を公開版とmainで区別 |
| P0全体 | P0-A/P0-Bで確定した操作列を変更の影響範囲に応じて再実行。再利用する証拠は元SHAと差分理由をreportへ記録 |

親が共有manifest・workflow・通常手順・最終統合を担当する。独立作業を別スレッドへ渡す場合は、上の契約、編集範囲、提出物、CI起動不要をまとめて渡す。担当ごとのCIや逐次小レビューはしない。

## CI・実機・文書の境界

初回は通常/生成比較の2 runを上限目安とし、各job見込み30分以下、timeout45分以下。診断の失敗例は同じjob内の期待失敗として検査し、失敗例ごとのActions runを作らない。具体的なコマンドとselectorは実装を揃えてからcheck-delivery reportに固定する。

0.7.0候補では寿命・選択復元/リセット・B保持、同意、無効化/再有効化/削除/取消/再試行、提示/UIKit、Widget状態/Shortcut拒否と回復をまとめて実機確認する。候補IPAの取得・展開/CRC検査も配布前に行う。各小タスクでユーザーへ実機を依頼しない。

minor更新時の全文書監査とrelease gateを通す。P0全体の確認前に版を0.7.0完了へ繰り上げない。ユーザー側の別途調査が0.7.0完了時までに未反映なら提供を要求し、1.0の対象範囲はその後に判断する。
