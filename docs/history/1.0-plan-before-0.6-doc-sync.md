# JibunKit 1.0 完成計画

**2026-09-09再評価: 1.0未達・公開保留。既存の成功項目は部分的な検証証拠として保持する。完成基準は、最初からJibunKitを前提に開発する幅広いアプリの非干渉共存。未要求・複雑・サンプル不在を理由に必要な共通機構を先送りしない。[制約と未対応の棚卸し](../coexistence-boundaries.md)を追加条件とする。**


更新日: 2026-09-09

ユーザーの依頼はJibunKit v1.0完成。個別CI成功やチェックポイントで全体作業を終了しない。設計原則は既存の1.0方向文書を継承し、この計画で実装・検証・出荷の残作業を管理する。通常の技術選択と順序は実装側で判断する。重要な仕様変更・データ互換性の破壊は判断材料を揃えてユーザーへ確認する。

## 1.0.0の上位完成基準

> JibunKitへ統合した結果、独立アプリならOSやアプリ境界によって得られていた隔離・調停・所有権管理が失われるなら、その差分をJibunKitが可能な範囲で補う。

「可能」は技術的可能性で判断する。複雑・未要求・サンプル不在による先送りは未達として残す。各領域で独立時の保証、統合で失う差分、補完実装、競合/取消/終了/復帰の検証、補えない部分の根拠を記録する。既存のV1〜V6の成功だけでは1.0に到達しない。

## 完成を判断する条件

| ID | 条件 | 必要な証拠 |
| --- | --- | --- |
| V0 | 統合で失われる隔離・調停・所有権管理を技術的に可能な範囲で補完する | 差分台帳、補完実装と複数Featureの非干渉検証、残存制約の根拠。未対応・未調査を合格にしない |
| V1 | 独立Swift/SwiftUI Featureを、単独版とJibunKit版で同じ実装から開発・実行できる | 雛形、接続手順、単独起動・ホスト共存のCI。既存コードの分離手順と責任境界 |
| V2 | 複数画面・構造化データ・添付ファイルを持つ実用規模のFeatureで基盤の制限を検証する | 編集・再起動・検索または詳細遷移・他Featureとの独立保存。単純なText雛形だけを証拠にしない |
| V3 | データを保って更新・復旧できる | Featureごとのバックアップ、schema移行、破損拒否、選択外の維持、添付ファイルを含む復旧、失敗状態の説明 |
| V4 | システム連携をFeatureへ接続できる | Widget、App Intents、複数通知、URLの接続手順・CI・出荷候補IPAでの実機確認。OS/署名由来の制約と基盤の未対応を区別 |
| V5 | 作者へ都度相談せず追加・更新・運用できる | WindowsからActionsを使う手順、依存・権限・保存先の分離、基盤更新時の互換性方針、例とテストの対応 |
| V6 | 検証したsourceと配布物が一致する1.0を届ける | 出荷候補の全CI、対象commit、版番号、変更履歴、実機結果、最終公開手順とrelease asset |

自動変換器、動的IPA実行、ストア、クラウド同期、全機種保証は追加しない。Featureの機能・画面数・保存方式を固定しない。検証用アプリが動くことと製品の完成は区別する。

## 保持するもの

既存Counter/ReminderのID・保存値・通知IDとバックアップ形式の読込み互換性を維持する。Zaikoのignoredローカルsource/testsは保持し、製品へ戻さない。既報のupstream issueを重複作成しない。参照Featureは追加開発の実例として扱い、ユーザーの個別アプリを勝手に選定・移植しない。
