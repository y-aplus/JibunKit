## CI境界を先に固定する

| 境界 | 実装する単位 | 合格までに確認する範囲 | 初回CIの上限目安 |
| --- | --- | --- | --- |
| P0-A 寿命・保存・終了診断を通常経路で閉じる | P0-1 / P0-3 / P0-6 | P0-1 / P0-3 / P0-6 | 2 run |
| P0-B 画面提示・同意・無効化削除のアプリ内操作 | P0-2 / P0-5 | P0-1 / P0-2 / P0-3 / P0-5 | 2 run |
| P0-C 追加更新経路とP0全体の0.7.0出荷 | P0-4 | P0-1 / P0-2 / P0-3 / P0-4 / P0-5 / P0-6 | 2 run |
| P1-A 共有入力・Shortcuts・静的WidgetのOS入口 | P1-3 / P1-1 / P1-2 | P0-1 / P0-2 / P0-3 / P0-4 / P0-5 / P0-6 / P1-1 / P1-2 / P1-3 | 3 run |
| P1-B 通知・HTTP・Webの実利用と0.8.0出荷 | P1-4 / P1-5 / P1-6 | P0-1 / P0-2 / P0-3 / P0-4 / P0-5 / P0-6 / P1-1 / P1-2 / P1-3 / P1-4 / P1-5 / P1-6 | 3 run |

各境界はAPI・fixture一つではなく、複数の契約、通常Feature接続、失敗/取消、二ownerの非干渉、利用手順を含む。
P0-Cは単独のP0-4実装に加えてP0全体の出荷確認を扱う。P1-Aでは新規開発量の大きい共有入口を先に設計する。
上限は予算であり空のrunを埋める割当ではない。CI失敗や安全な並列分割が必要なら理由を残して増やす。
一境界を複数run/jobへ分けた場合は実数を記録し、「1バッチ」と呼んで消費を隠さない。
チェックポイントcommit/pushとCI境界を分離し、各小変更・子の提出ごとにCIを走らせない。
途中のCI境界では実機専用条件を対応minorの候補へ予約できるが、その単位をcompleteにはしない。P0-C/P1-Bの出荷判断までに閉じる。
詳細は[大きなCI単位の運用](ci-boundaries.md)。

需要調査は従前どおりユーザー側のChatGPT調査を前提とし、この変更では調査スレッドを新設しない。
JibunKit採用に結びつく用途・導入断念要因・代替・署名/周辺機器/外部サービス前提・残実装/OS検証/保守負荷を整理する。
その根拠から単位ごとに1.0へ含める/後段へ送る/追加調査を提案し、ユーザーが最終境界を決める。決定までは1.0出荷gateを閉じる。

## 状態と証拠

優先度、実装状態、出荷対象は別軸。P0/P1の単位が完了しても親Dを一括完了にしない。
plan.jsonのpartialは残実装がある状態。completeへ変更するには合格条件ごとの証拠とレビューが必要。
標準API・unit・Simulator・実機の証拠を分離し、対象source、操作、観測、残件を記録する。
2026-09-13時点、P0-A/P0-Bの非実機条件は通常/生成CIで確認してmainへ反映。P0-Cの追加診断・片側Package更新を含む0.7.0 build 8候補の初回CI34704117433と次の34704681281が失敗し、検証コードを修正して一括再検証する。共通244試験は34704681281で成功したが、生成/iOS更新は未実行。実機専用条件、artifact、配布整合性も未確認のため全P0は完了にしない。需要調査は別途実施中で、0.7.0完了時までに未反映ならユーザーへ結果の提供を依頼する。
