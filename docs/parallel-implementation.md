# 大きなCI境界での並列実装

更新日: 2026-09-12。[Issue #5の優先順位](implementation-priorities.md)と[CI境界の手順](ci-boundaries.md)を適用する。
2026-09-12のユーザー指示によりP0-A実装を再開。以下の大きな境界と分担を適用する。

## 分担と提出の単位

最大3レーン。親は共通契約・統合と自身の実装を担当し、独立した実装・検証を別スレッドのSol low等へ任せる。
サブエージェントは使わない。高難度の未解決問題だけ必要に応じてモデル/労力を見直し、空き枠を埋めるために仕事を作らない。
各レーンへ小API単位で逐次指示せず、P0-A等の境界内で独立して閉じられる実装・接続・失敗試験・説明までを渡す。
親も実装を継続し、担当者の細部判断や進捗報告を頻繁に再確認しない。

## 着手時に一度揃える契約

各CI境界の着手前に、親が担当者と次を一つの記録へ固定する。

- 共通baseline commit、対象P単位/親D、担当ファイルと共有ファイルの編集者。
- APIの入力/出力/エラー、ownerと登録/解除、開始/取消/終了/再開の順序。
- 通常Feature入口、二owner比較、破損/拒否/中断/再入/失敗時に保持すべき状態。
- 既存証拠の参照元、新しい操作列と期待値、変更で無効になる証拠の範囲。
- CIのrun/job分割、実機確認のまとまり、提出形式と合格条件。

MiniAppContext/Runtime/Definition、Registry、Package/Project manifest、workflow、台帳等の共有変更は一人が所有する。
共通契約を先に確定し、必要ならCI未確認と明記した共通commitを境界用統合ブランチへ置く。
そのcommitごとにCIは要求しない。兄弟ブランチを多段に依存させず、全員が同じ契約baselineを使う。
契約に本質的な変更が出たときだけ、影響する担当へまとめて伝え直す。

## 一括提出と一括レビュー

担当はローカルで可能な検証を済ませ、境界の実装・接続・試験案が揃ったところで提出する。
提出物はcommit、変更した契約、合格条件とtest対応、ローカル結果、未検証範囲、CI入力案の一式。
親は全レーンを統合した差分と試験内容を**CI前に一括レビュー**し、指摘もまとめて返す。
基本は初回提出と一括修正の1往復。通常の指摘修正は担当の自己検証と親の該当差分確認で閉じ、毎回全体をレビューし直さない。
データ所有権・公開契約・失敗時保証・assertionの意味が変わった場合は再レビューする。必要な修正を回数上限で省略せず、往復増加の原因を記録する。

checkpoint commit/pushは随時可能だが、子の提出・小タスク完了・commitごとにCIを起動しない。
通常は統合ブランチをimmutable SHAへ固定し、その境界に必要なCIをまとめて依頼する。
CI未確認の製品変更を検証済みmainとして扱わない。今回の文書/toolだけの変更はローカル検証で扱える。

## CI中と失敗時

CI担当は指定されたSHA・試験群の実行と証拠整理を持ち、未合意の契約変更をCI結果で既成事実化しない。
待機はOS側の完了監視とcodex queue等の一回通知に任せる。`gh run watch --interval`、モデルによる定期poll、待つだけのレビュー往復は禁止する。
既存監視スクリプトの設定はローカルに保ち、トピック・権限オプション・長い実装指示をqueueへ書かない。
完了通知にはrun ID/結果だけでよく、継続範囲は版管理した境界記録を参照する。

CI待ちに独立した次の実装を進めてよいが、未検証の契約へ依存する実装は仮定を明記する。
失敗時は全jobの証拠を集めて原因をまとめ、無関係な成功jobを止めない。詳細は[再実行規則](ci-boundaries.md#失敗後の再実行)に従う。

## 実績による見直し

各境界で、受入済みP単位、実際のrun/attempt数・job時間、親の提出/修正メッセージ数、レビュー往復数、契約不一致と環境失敗の回数を記録する。
最初のP0-A完了時と以後各minor時に前の運用と比較し、CI待ち・親管理・重複作業が減ったかを確認する。
料金/トークン実績が取得できなければ節約率は断定しない。親の管理量を減らせていなければ委譲を広げるかレーンを減らす。
数値を良くするために試験や契約レビューを省略しない。

[停止時の引継ぎ](verification/2026-09-12-development-checkpoint.md)に既存レーンのbranchと証拠を保持する。
