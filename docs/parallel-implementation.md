# 台帳実装の並列運用

更新日: 2026-09-10

JibunKit 1.0の統合差分台帳を進める際は、**常に3人を実装へ張り付けることではなく、mainへ統合済みの補完単位を増やすこと**を目的にする。並列数は最大3とし、その時点のボトルネックに応じて実装・検証・統合へ枠を再配置する。

この運用は[`coexistence-ledger.md`](coexistence-ledger.md)の完成条件やD項目の意味を変更しない。並列化を理由に未対応・未調査を合格扱いしない。

## 基本方針

- 同時に進める作業レーンは**最大3**とする。3枠を埋めること自体を目標にしない。
- 導入初期は、原則として**2実装 + 1検証経路改善**で始める。
- 検証経路の律速が十分に下がったら、第三枠を実装へ戻し、**最大3実装**まで使う。
- 以後は固定編成にせず、統合待ち、CI往復、手戻り、共通契約の依存など、その時点の滞留箇所へ枠を移す。
- 独立して進められる作業がないときは、無理に並列化しない。競合を作るより空き枠を許容する。

## 作業単位

一つのレーンには、D項目全体ではなく、必要に応じて**意味のある補完単位**を割り当てる。担当は、その補完単位について可能な限り次を一続きで持つ。

1. 対象D番号と失われる境界の確認
2. 契約・責任境界の確定
3. 実装
4. 対象を直接確認するfocused test / fixture
5. 検証結果・未確認範囲の記録

単独成功や登録APIの追加だけで、D項目全体の完了に繰り上げない。

## 共通契約は直列化する

複数レーンが同じ共通契約を別々に変更しない。

`MiniAppContext`、`MiniAppRuntime`、`MiniAppDefinition`、共通routingや所有権モデルなど、複数レーンの前提になる変更が必要な場合は、影響する作業を一度止め、**一人の担当が共通変更を先にmainへ統合**する。その後、各レーンは最新mainを前提に再開する。

未マージの兄弟ブランチを互いの依存先にしない。長期間の多段ブランチ依存を作らない。

## 共有ファイルの扱い

次のような衝突しやすいファイルは、同じ変更期間中に複数レーンが並行編集しない。

- `Package.swift`
- `Project.swift`
- `.github/workflows/*`
- 共通Registry / host wiring
- `docs/coexistence-ledger.md`
- CHANGELOGや共通設計文書

必要な変更は、統合担当または明示した一レーンへ集約する。各レーンは、自分の実装・unit test・fixture・検証記録をできるだけ担当固有のファイルへ置く。

## 検証経路

初期の第三枠は、各実装レーンが**無関係な長時間試験を毎回待たずに、自分の変更を短い経路で確認できる状態**を作ることに使う。

新しいCI基盤を目的化しない。既存のworkflow input、test filter、job分離などで足りる場合はそれを使い、必要な不足だけを補う。

開発中はfocused testを優先し、次の節目では必要な回帰検証を行う。

- mainへ統合する前
- 共通契約を変更したとき
- 複数D項目の境界が交差したとき
- release候補を作るとき

focused testの成功を全回帰成功として扱わない。ビルド・Simulator・実機確認も、それぞれ別の証拠として記録する。

## レーンの再配置

担当分野の知識継続のため、寿命・データ、画面・イベント、共有資源などの大まかな担当軸を持ってよいが、永久固定しない。

次の兆候を見て枠を再配置する。

- **実装済みブランチが統合待ちで溜まる**: 一枠を統合・回帰確認へ回す。
- **無関係なCI失敗や長い再実行が反復する**: 一枠を検証経路の改善へ回す。
- **複数レーンが同じ共通API変更を必要とする**: その共通変更を直列化する。
- **検証経路が安定し、独立した補完単位が複数ある**: 最大3実装へ戻す。
- **依存関係が強く、分割すると設計が二重化する**: 無理に並列化しない。

## 初期配置

この方針を採用する時点では、次の形から開始する。

- 実装レーン1: 最新台帳から、他レーンと共通契約変更を必要としない優先度の高い補完単位
- 実装レーン2: 別の独立した補完単位
- 検証レーン3: lane-specificなfocused verificationを短く独立に実行できるよう、既存CI経路の不足を最小限修正

検証レーン3の目的が達成されたら、その枠を次の独立実装へ移す。具体的なD番号はこの文書へ固定せず、着手時の最新[`coexistence-ledger.md`](coexistence-ledger.md)から選ぶ。

## 完了の測り方

評価対象は、エージェント数、commit数、PR数、テスト数ではない。

**補完単位が、必要な検証と証拠を伴ってmainへ統合されるまで**を一つの成果として扱う。並列化の効果は、着手から統合までの時間、CI待ち、統合後の手戻り、未統合成果の滞留を見て判断する。

3並列が常に最適であるとは仮定しない。実測上、2並列や一時的な直列化の方が早ければ、その編成へ切り替える。
