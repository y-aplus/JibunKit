# 台帳実装の並列運用

更新日: 2026-09-12

運用状態: ユーザー指示により全開発スレッドは停止中。[停止時引継ぎ](verification/2026-09-12-development-checkpoint.md)を参照。以下は明示再開後の運用規則であり、新規着手の指示ではない。

JibunKit 1.0の統合差分台帳を進める際は、**常に3人を実装へ張り付けることではなく、mainへ統合済みの補完単位を増やすこと**を目的にする。並列数は最大3とし、その時点のボトルネックに応じて実装・検証・統合へ枠を再配置する。

この運用は[`coexistence-ledger.md`](coexistence-ledger.md)の完成条件やD項目の意味を変更しない。並列化を理由に未対応・未調査を合格扱いしない。

## 基本方針

2026-09-11更新: CIが律速のため、**CI前レビューを先に済ませる**。この規則は以下の
旧運用にある「実装・テスト・証拠まで完了してから初回提出」より優先する。
待機中のモデル実行は行わず、`gh run watch --interval`は禁止する。

- 同時に進める作業レーンは**最大3**とする。3枠を埋めること自体を目標にしない。
- 導入初期は、原則として**2実装 + 1検証経路改善**で始める。
- 検証経路の律速が十分に下がったら、第三枠を実装へ戻し、**最大3実装**まで使う。
- 以後は固定編成にせず、統合待ち、CI往復、手戻り、共通契約の依存など、その時点の滞留箇所へ枠を移す。
- 独立して進められる作業がないときは、無理に並列化しない。競合を作るより空き枠を許容する。

## 作業単位

一つのレーンには、D項目全体ではなく、必要に応じて**意味のある補完単位**を割り当てる。担当は、その補完単位について可能な限り次を一続きで持つ。

1. 対象D番号と失われる境界の確認
2. 契約・責任境界の確定
3. 実装
4. 対象を直接確認するfocused test / fixture
5. 検証結果・未確認範囲の記録

単独成功や登録APIの追加だけで、D項目全体の完了に繰り上げない。

## 共通契約は直列化する

複数レーンが同じ共通契約を別々に変更しない。

`MiniAppContext`、`MiniAppRuntime`、`MiniAppDefinition`、共通routingや所有権モデルなど、複数レーンの前提になる変更が必要な場合は、影響する作業を一度止め、**一人の担当が共通変更を先にmainへ統合**する。その後、各レーンは最新mainを前提に再開する。

未マージの兄弟ブランチを互いの依存先にしない。長期間の多段ブランチ依存を作らない。

## 共有ファイルの扱い

次のような衝突しやすいファイルは、同じ変更期間中に複数レーンが並行編集しない。

- `Package.swift`
- `Project.swift`
- `.github/workflows/*`
- 共通Registry / host wiring
- `docs/coexistence-ledger.md`
- CHANGELOGや共通設計文書

必要な変更は、統合担当または明示した一レーンへ集約する。各レーンは、自分の実装・unit test・fixture・検証記録をできるだけ担当固有のファイルへ置く。

## 検証経路

初期の第三枠は、各実装レーンが**無関係な長時間試験を毎回待たずに、自分の変更を短い経路で確認できる状態**を作ることに使う。

新しいCI基盤を目的化しない。既存のworkflow input、test filter、job分離などで足りる場合はそれを使い、必要な不足だけを補う。

開発中はfocused testを優先し、次の節目では必要な回帰検証を行う。

- mainへ統合する前
- 共通契約を変更したとき
- 複数D項目の境界が交差したとき
- release候補を作るとき

focused testの成功を全回帰成功として扱わない。ビルド・Simulator・実機確認も、それぞれ別の証拠として記録する。

## レーンの再配置

担当分野の知識継続のため、寿命・データ、画面・イベント、共有資源などの大まかな担当軸を持ってよいが、永久固定しない。

次の兆候を見て枠を再配置する。

- **実装済みブランチが統合待ちで溜まる**: 一枠を統合・回帰確認へ回す。
- **無関係なCI失敗や長い再実行が反復する**: 一枠を検証経路の改善へ回す。
- **複数レーンが同じ共通API変更を必要とする**: その共通変更を直列化する。
- **検証経路が安定し、独立した補完単位が複数ある**: 最大3実装へ戻す。
- **依存関係が強く、分割すると設計が二重化する**: 無理に並列化しない。

## 初期配置

この方針を採用する時点では、次の形から開始する。

- 実装レーン1: 最新台帳から、他レーンと共通契約変更を必要としない優先度の高い補完単位
- 実装レーン2: 別の独立した補完単位
- 検証レーン3: lane-specificなfocused verificationを短く独立に実行できるよう、既存CI経路の不足を最小限修正

検証レーン3の目的が達成されたら、その枠を次の独立実装へ移す。具体的なD番号はこの文書へ固定せず、着手時の最新[`coexistence-ledger.md`](coexistence-ledger.md)から選ぶ。

## 完了の測り方

評価対象は、エージェント数、commit数、PR数、テスト数ではない。

**補完単位が、必要な検証と証拠を伴ってmainへ統合されるまで**を一つの成果として扱う。並列化の効果は、着手から統合までの時間、CI待ち、統合後の手戻り、未統合成果の滞留を見て判断する。

3並列が常に最適であるとは仮定しない。実測上、2並列や一時的な直列化の方が早ければ、その編成へ切り替える。

## モデル分担と連絡（2026-09-10採用）

初期の3レーンは、統合担当を兼ねるAstra lowの実装1、Sol lowの独立実装2、Sol lowの検証経路改善とする。統合担当自身も実装し、レビュー/統合が滞ったら担当実装を減らす。

ワーカーは別スレッドと専用branch/worktreeで動かす。サブエージェントは使わない。通常の判断を統合担当へ逐一返さず、意味のある補完単位を実装・テスト・証拠まで担当する。完了、共通契約依存、重要な判断が必要な場合に連絡し、短い間隔で状態確認を繰り返さない。CIは独立バックグラウンド監視からの完了通知で再開する。

通常はSol lowで進め、設計の未解決や原因を絞れない手戻りが続く作業だけ労力や担当を変更する。CI失敗だけを理由に上位モデルへ切り替えない。全履歴を毎回共有せず、対象契約・完成条件・担当範囲・必要な資料を渡す。最初の数補完単位で、消費量・統合までの時間・統合担当による修正量を見て配分を調整する。

### 初回の運用点検

初期3レーンの成果（Feature経路保持、購読所有権、限定検証経路）がmainへ統合された時点で、統合担当がこの体制の初回点検を行い、ユーザーへ報告する。途中で統合待ちや管理負担が明らかに膨らんだ場合は、その時点で前倒しする。点検自体を目的に実装を止めたり、定期的な状態取得を増やしたりしない。

確認するものは、各補完単位の着手から統合までの時間、CI待ち・再実行、レビュー後の手戻り、統合担当の管理・修正負担、取得可能なモデル別利用量。初回のスレッド作成・権限調整の負担は継続運用の負担と分ける。比較対象の直列開発と作業難度が異なることも明記する。

API単価をPro利用枠の消費比率へ換算せず、取得できない費用・利用量は不明とする。節約を断定できない場合でも、管理負担を含めて継続・分担変更・並列数削減のどれが妥当か判断する。

### 再点検後の分担

[2026-09-11の再点検](verification/2026-09-11-parallel-operation.md)では、D15/D16の初稿がCI成功後にも寿命・完了契約の修正を要し、親の管理負担が大きかった。モデルはAstra low / Sol lowを維持し、共通callbackの所有権・寿命設計は親へ集め、ワーカーは独立native比較と契約確定後の実装・検証へ寄せる。意味のある補完単位を並行させる原則は維持し、節約率は未確定とする。

### CI前レビューとモデルを使わない待機

1. 委譲時に統合担当が責任境界と必要な挙動を具体化する。担当は通常の実装判断を進め、
   差分・必要なテスト・ローカルで可能な確認を一まとまりにしてCI前に提出する。
2. 統合担当は契約、実装、試験のassertionが示す範囲を一緒にレビューする。単なるbuildや
   同一processの読出しをOS配送・process間の隔離と混同していないかも、この時点で確認する。
   指摘はまとめて返し、細切れの修正ごとにCIを起動しない。
3. 修正を反映した対象commitと検証範囲を統合担当が確定してからCIを一括実行する。
   ワーカーはレビュー前に新規CI/再CIを回さない。これは内部の作業調整であり、通常のCIに
   ユーザー承認を求める手順ではない。現在走っているCIは契約変更だけで捨てず、証拠を読む。
4. CI状態の監視はモデルを呼ばない独立バックグラウンド処理が持ち、終了したときだけ
   `codex queue`で担当へ結果を送る。モデルのターンでwatch/sleep/pollを繰り返さない。
   `gh run watch --interval`は使用しない。監視と完了通知の重複も防ぐ。
5. 結果到着後は確認できた挙動・失敗箇所を担当が整理する。再実行前に、変更と次の検証で
   解決する問いをまとめて統合担当へ返す。合格後は差分がレビュー対象commitと一致することと
   実際の証拠を確認し、初めて本格的な契約レビューを始める順序には戻さない。
6. CI完了後のログ取得・原因調査・修正準備は担当が自律的に進める。統合担当からログを
   渡されるまで待つ必要はない。再レビューを待つ対象は、まとめた修正と次のCIの範囲である。
   CIやレビューだけを待つ段階ではターンを終了し、完了通知や統合担当からの返信で再開する。
   `wait_threads`や`read_thread`の反復で待機を維持しない。

CI前レビューでコンパイルやOS挙動を証明したとは扱わない。CI後に初めて分かった問題は
その証拠に基づき直すが、実行前に読める契約不一致のために高価なCIを往復させない。
