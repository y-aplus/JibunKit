## 1. 製品像と0.1の範囲

**利用者が欲しいものは、自分で作ったミニアプリを束ねて使えるスーパーアプリ。** 自分の用途に合わせて無理なく開発する利用者（ゆる開発者）が、ミニアプリを追加して育てられる基盤を作る。SideStoreで使う1本のネイティブiOSアプリとして提供し、Gitで管理してGitHubでオープンソースソフトウェアとして公開・保守する。

ミニアプリは、それぞれ目的、画面、操作、データを持つ利用単位とする。単一の操作や画面だけに限定せず、複数の画面・機能を含めてよい。内部ではビルド時に組み込む機能単位（Feature）として実装するが、利用者向けにはミニアプリとして説明する。既存IPAをそのまま独立実行する仕組みを意味するものではない。

0.1は個別アプリの移植ではなく、スーパーアプリの基盤と説明用の最小サンプルを対象にする。既存の旅行アプリ等を母体にするための査定・移植は行わない。公開対象は、利用者が派生させて自分用のミニアプリを追加できる、継続更新する基盤アプリとする。サンプルを簡単にするのは基盤の検証のためであり、追加できるミニアプリの用途や構成をサンプルと同程度に限定するものではない。

優先するのは、SideStoreで実際に使えること、ミニアプリ追加の変更箇所が少ないこと、更新の取り込み方と対応条件を説明できること。汎用フレームワークを作ること自体は目的にしない。

| --- | --- |

### 0.1の完成条件を動かさないための規則

- **0.1の完成には、第6節の全必須条件と第8節の成果物が必要。** 一部の動作、ビルド成功、サンプルだけの完成、文書だけの整備では、基盤全体を完成扱いにしない。
- 対象バージョンは **0.1** とする。確定済みのF1〜F7・O1〜O4をそのまま0.1の完成条件に対応付ける。「MVP」「ver 0」「0.x」などの別名で条件を曖昧にしたり、必須項目を減らしたりしない。「0.x」はバージョン系列についての表記であり、個々の版の完成条件を代替しない。
- 作業を複数段階に分けても、必須項目は0.1の未完了作業として残る。「後の版で対応」と書き換えて完了に数えない。進捗は項目ごとの未着手・作業中・未達・合格と、その根拠で示す。
- 必須項目の削除・縮小・延期には、対象、理由、利用者への影響、代案、変更後の完成条件を示し、ユーザーの明示的な合意を得る。元の条件と変更履歴を残す。名称変更や実装担当者の判断だけで範囲を変えない。
- 技術的に成立しない場合は、未達の機能と原因を明記する。第7節の中断条件に従い、実現手段か要件の変更判断に戻る。成立性検証を繰り返すだけで、必須機能を無期限の将来作業へ移さない。
- 対象外とした機能は、0.1の完成に不要なものとして明示する。将来の実装を約束した意味ではない。0.1で必須の機能と混ぜない。

### 機能と技術の判断を分ける

ユーザーは技術方式より、使える機能を優先する。設計への合意を、実装技術の細部を読んで正しさを保証したものとして扱わない。技術の選択・調査・検証は実装側が担う。ユーザーへの確認は「何ができるか、何ができなくなるか、操作・費用・手間がどう変わるか」で説明する。

完成条件を保つ内部構成の調整と、利用者への約束を変える要件変更を区別する。新たな費用、Mac購入、必須機能の縮小などを、単なる技術選択として進めない。

### 0.1から1.0へ育てる設計原則

0.1はその後も継続して育てる基盤とする。1.0で別路線へ進んで単純に破棄することが分かっている、0.1専用の仕様は作らない。一方、基本はYAGNI（今必要でないものは作らない）とし、将来の要求を先回りした拡張口や汎用機構は作らない。

今の完成条件に必要な責務分担、ミニアプリの追加方法、保存と更新の境界を整える。カウンターはその構成を使うサンプルであって、本体の仕様をカウンター専用にしない。未知の要件まで予測したり、すべての内部構成の永久互換を保証したりするものではない。

実証で問題が分かれば構成を修正する。その場合は理由・影響・移行方法を記録する。一時的な成立性の検証物と、継続して使う製品実装を区別する。詳細は[1.0の目標案と設計原則](2026-08-28-appbaseios-1.0-direction.md)に記載する。

### バージョンの表記

会話・設計の対象は引き続き **0.1** と表記する。`v`や`ver`はバージョンであることを示す補助表記で、必須ではない。厳密なリリースの識別には3要素の番号を使う。[Semantic Versioning](https://semver.org/spec/v2.0.0.html)

| 場所 | 表記方針 |
| --- | --- |
| 会話・設計・目標 | 0.1、1.0 |
| 個々のリリースとアプリのバージョン値 | 0.1.0、修正版は0.1.1のように区別する。 |
| Gitタグ | `v0.1.0`の形式を使う案。`v`はタグ名の一部で、番号本体とは分ける。 |

Appleの`CFBundleShortVersionString`も数値3要素の形式を規定している。別途ビルドを識別する値を設け、タグ・IPA・検証記録を対応付ける。ここで0.1を0.1.0へ細分化して表記することは、完成条件を変える意味ではない。[Appleのバージョン値](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring)

### 確認済みの区別

- クラウド上の補助ビルドに関する一時的な保留は、実行場所を省略した説明によるものだった。実行場所とMac購入不要を説明し、元の条件付き採用方針を確認した。利用拒否や採用撤回として扱わない。
- 設計案の採用と技術的な正しさの検証を分ける。基盤構成は提案として認められたもので、ユーザーが動作を保証したものではない。
- 実証サンプルの具体的な操作と合格条件も確認済み。設計への合意を実装・環境構築・公開操作の許可へ読み替えない。
- 設計確認後、ユーザーからGit管理の開始とGitHubへの送信を明示的に依頼され、送信前に非公開の指定があった。公開時期は0.1の完成・リリースに合わせる。今回は非公開保存のみを行う。この作業環境ではアプリ実装・ビルド環境構築を行わず、文書を引き継ぐ。

## 4. 公開基盤と個人用リポジトリ

公開基盤には共通部分、説明用のサンプルミニアプリ、検証、導入・更新・貢献の文書を置く。将来の個人用スーパーアプリと自作ミニアプリは、基盤のGit履歴を引き継いだ独立した非公開リポジトリに置く。

GitHubの通常のFork機能では、公開リポジトリから作るForkも公開になる。今回の非公開の派生側は、そのFork機能とは区別する。公開基盤を `upstream` として登録し、共通のGit履歴を使って更新を取り込む設計とする。[GitHubのForkの可視性](https://docs.github.com/en/pull-requests/reference/forks)

自作ミニアプリのコードを公開するかどうかと、共通基盤の改善を公開側へ戻すかどうかを分ける。秘密情報、署名鍵、認証情報、実データは、非公開リポジトリであっても保存しない。

0.1では、利用者に「依存バージョンを上げるだけで更新できる」ことや「自動で競合を解消できる」ことは約束しない。更新時には差分確認、必要な競合解消、自動チェックと実機確認を行う。

## 5. スーパーアプリ基盤とミニアプリの内部構成

この節では、スーパーアプリ本体をホスト、ミニアプリの実装単位をFeatureと呼ぶ。利用者向けの製品像と、内部構成を説明する語を区別する。

| 部分 | 担当すること | 担当させないこと |
| --- | --- | --- |
| ホスト | 起動、ランチャー、ミニアプリ一覧の登録、画面遷移、設定・ライセンス表示、外部からの入口。 | 個々のFeatureの業務処理・保存形式。 |
| Feature | 画面、状態、処理、保存形式。同じ処理を画面とApp Intentから利用できるようにする。 | 他のFeatureの保存データの直接操作。 |
| 必要最小限の共通部分 | 機能ID、登録情報、通知・外部起動の行き先、実際に必要な共有データ型。 | 使用例のない汎用StorageService・NetworkingService等の先行実装。 |
| App Intentの入口 | ホスト側で登録し、入力をFeatureへ渡し、結果を返す。 | Featureと重複する処理の実装。 |
| Widgetの拡張 | 共有された表示用データを読む。 | 0.1でのデータ書込みや独立した業務処理。 |

### ミニアプリ追加と変更の境界

- ミニアプリはビルド時に登録する。遠隔からコードを追加する仕組みは作らない。
- 通常のFeature追加では、Featureのコード、追加用の登録箇所、必要なビルド宣言を変更する。ホストの共通処理の書換えを要求しない構成を目指す。
- WidgetやApp Intentを追加する場合は、それぞれの登録・ビルド設定も必要になる。通常画面の追加と同じ変更量だとは約束しない。
- 機能IDを保存先・通知ID・外部起動先の名前空間に使う。ID変更はデータやリンクの移行を伴う変更として扱う。
- 小さいFeatureはフォルダで開始し、すべてを独立した公開Swift Packageにしない。アプリ本体とWidgetは別のビルド対象にする。
- Swift Package Managerを中心に構成する案を採用するが、App Intentのメタデータ生成やテストの実行方法を含む具体的なターゲット配置は、最初の成立性検証で確定する。
- 権限はその機能を使う操作の時に要求する。Featureのフォルダ分離を、iOSの権限やプロセスの隔離として説明しない。

### 技術確認から具体化した注意点

- SideStore再署名後の共有領域の識別子を、本体とWidgetで同じように解決する。ビルド前の識別子を固定して読めるとは仮定しない。
- 画面とショートカットの更新処理を共通にし、保存の競合を防ぐ。起動直後にも依存先が準備される構成にする。
- 通知の受け取り口はホストに集約し、終了状態からの起動でも、画面の準備後に該当ミニアプリへ移動できるようにする。
- ミニアプリID・保存先・通知ID・起動先の重複を検査する。ミニアプリ一覧への登録と、ショートカットのメタデータ生成・登録は別に検証する。

根拠、ソースの版、未検証箇所、確認順は[技術確認文書](2026-08-28-appbaseios-technical-review.md)に分けて記録する。これらは確定済みの完成条件を実現するための内部設計の補足であり、追加の製品機能や動作実証ではない。

### 0.1で作らないもの

既存IPAの動的実行、ミニアプリのストア、汎用プラグイン機構、クラウド同期、利用者アカウント、個別アプリの移植、使用例のない共通サービス、全Featureの公開ライブラリ化は対象外とする。

| ID | 検証対象 | 合格条件 |
| --- | --- | --- |
| F1 | 起動・保存 | スーパーアプリ内のミニアプリ一覧からサンプルを開ける。カウンターの値を変更し、スーパーアプリを再起動しても値が残る。 |
| F2 | ショートカット | 独自操作が実機のアクション一覧に現れる。数値を受け取り、画面操作と共通の処理で値を更新し、結果をショートカットへ返す。URLで画面を開くだけでは合格にしない。実行中にアプリ画面が開いてもよい。 |
| F3 | Widget | アプリ側の保存値を共有領域経由で表示する。表示専用でよい。更新要求とOSによる表示更新を区別し、即時更新は必須にしない。 |
| F4 | ローカル通知 | 利用者の操作で予約し、通知から該当ミニアプリへ戻れる。許可の拒否を扱い、スーパーアプリ起動だけで許可を要求しない。 |
| F5 | 第2のミニアプリの追加 | カウンターの保存先や起動先と衝突せず、スーパーアプリ本体の共通処理を書き換えずに追加できる。追加したミニアプリも一覧から開ける。 |
| F6 | SideStore導入・更新 | 無料のAppleアカウントで、SideStoreによる再署名・インストールができる。更新インストールと署名更新後も、保存値、Widget、ショートカット、通知からの起動が保たれる。 |
| F7 | Mac購入不要のビルド手順 | まずWindows上のWSLで検証する。不成立の場合だけGitHub Actionsが提供するクラウド上のmacOS環境を使い、F1〜F6を満たすIPAを作成できる手順を確立する。ローカル不成立時は理由を残す。 |

導入する本体と拡張、使用する識別子、アプリ枠とApp IDの消費を記録する。アプリ本数・拡張数・App ID数を同一視しない。

最初は申告された1台の組合せで実機確認する。機種・OS・SideStoreの表示バージョンを実行前に確認し、未検証の機種・OSまで対応済みと掲示しない。

合格とする際は、F1〜F7ごとに確認手順・期待結果・実際の結果・実行日・対象のソースとIPAの版・必要な実機条件を残す。自動チェックだけで実機での合格を代用しない。未達や未検証は、そのまま残す。

0.1の完成に含めない操作は、Widgetからの値変更、Widgetの即時更新保証、アプリ画面を開かないショートカット実行の保証。これらの除外は合意済みであり、F1〜F7の延期とは区別する。

### 検証の進め方と中断条件

実装開始の許可を得た後、既存ツールの利用条件・取得元・バージョンを確認し、最小アプリでビルド、IPA生成、SideStore導入、必須機能の実機動作を段階ごとに確認する。Apple SDKは正規の取得手順を用い、リポジトリや配布物に同梱しない。

許容する作業は既存OSSと薄い接続処理まで。ツール内部の改造や生成メタデータの手修正が必要になったら中断し、原因・不足機能・必要な追加作業を提示する。

ローカルで不成立の場合だけ、GitHub Actionsがクラウド上に用意するmacOS環境で補助ビルドする方針とする。Macの所有・購入は必要とせず、Windowsから操作する。生成したIPAの導入と動作確認は、手元のiPhoneとSideStoreで行う。

この条件付き採用方針は確認済み。実際に切り替える際は、ローカルでの不成立理由と必要な設定・利用枠を説明する。基盤の実装・環境構築自体はまだ開始していない。

ビルド環境の問題と、署名・会員種別・iOS・SideStoreの条件による問題を分ける。実行場所を変えれば権限上の制約も解決するとは考えない。必須の実機条件が満たせなければ、0.1を完成扱いにしない。[Appleの対応機能と会員種別](https://developer.apple.com/help/account/reference/supported-capabilities-ios/)

現在の方針では0.1の完成・リリースまで非公開とする。F1〜F7の実証とO1〜O4の公開前に揃える成果物・確認を終えた後、リポジトリの公開切替と0.1のリリースを同じ公開作業で行う。公開後にリポジトリ・タグ・IPA・文書の対応を確認して、公開を伴う条件も完了にする。非公開保存や版番号の付与だけでは達成扱いにしない。

### 運用上の規則

- 統合先は `main` とする案を採用する。変更は短い作業ブランチとプルリクエストで確認する。ブランチ作成前に必ずユーザーへ明示する。Git初期化も実施前に説明する。
- README、構成とミニアプリ追加の手順、ビルドとSideStore導入の手順、貢献手順、変更履歴、通常の問題報告と脆弱性報告の方法を整える。
- MITライセンスを採用する方針とする。第三者コード・依存ツールの利用条件と配布条件は別途確認する。
- 変更時には実行可能な自動チェックを行い、実機確認とは別に結果を記録する。ローカルで実行可能なチェックは手元で行う。iOSアプリ全体のビルドがローカルで成立しない場合、そのビルドにはGitHub Actionsがクラウド上に用意するmacOS環境が必要になる。Mac購入は前提にしない。
- 実機確認では端末、OS、SideStore、SDK、ビルドツール、ソースの版と結果を記録する。
- 認証情報、署名鍵、実データ、Apple SDK本体をGitや公開配布物に含めない。
- ソースを公開する時点で、開発中・未検証の範囲を明示する。0.1のリリースは、必須の実機合格条件を満たしてから行う。
- リリースのタグ、変更履歴、IPAとソースの版を対応付ける。利用者はSideStoreで再署名する。作者の個人証明書による署名を配布の前提にしない。
- 破壊的変更を明示し、移行が必要な箇所を説明する。0.xだから保存データを黙って破棄してよいとは扱わない。
- 個別アプリの移植対応、全環境の動作保証、長期の公開API互換性は0.1で約束しない。
- GitHubへの公開操作は承認を得てから行う。この設計への合意を公開操作の承認に転用しない。
