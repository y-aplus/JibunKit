# スーパーアプリ基盤 1.0の目標案と設計原則

更新日: 2026-08-28

**状態: 0.1からの継続性とYAGNIを設計原則として確認済み。以下の到達像は目標案であり、個別機能・完成基準・期限を一括承認されたものではない。IPA向けアダプタ・変換器は将来の検討候補。0.1の必須条件は変更しない。**

## 確定した設計原則

**0.1を1.0へ育てていく。1.0で別路線へ進み、単純に破棄することが分かっている0.1専用の仕様は作らない。基本はYAGNI（今必要でないものは作らない）。**

- 0.1で作るスーパーアプリ本体、ミニアプリの追加方法、保存データの扱い、検証・運用文書を、その後も育てる前提にする。カウンターのサンプルだけを成立させるために、本体をカウンター専用にしない。
- 将来の互換性を口実に、未使用の拡張口、汎用プラグイン機構、変換基盤などを先に作らない。今必要な責務分担と、ミニアプリの追加・更新の境界までを整える。
- 現時点で分かっている1.0の方向性との矛盾は、0.1の設計時に避ける。未知の要件を予測してすべて吸収する設計は求めない。
- 継続性は「すべてのコード・内部構成を永久に維持する」という意味ではない。実装・利用で判明した問題に対する変更は認めるが、理由、利用者への影響、既存ミニアプリとデータの移行方法を示す。将来の版だからという理由だけで全体を破棄しない。
- 成立性を調べるためだけの一時的な検証物は、継続して使う製品実装と区別する。検証物を作ったことを0.1の製品完成に数えない。

## 目指す状態

**ゆる開発者が、自分に必要なミニアプリを追加し、日常で使い、データを守りながらスーパーアプリと基盤を更新し続けられる。**

基盤の内部を毎回調べ直したり、作者へ都度相談したりしなくても、説明と実例を頼りに開発・運用を進められることを目指す。開発ではコード編集とビルドを行う前提を維持し、画面操作だけで何でも作れることは約束しない。

## 1.0に向けて確かめたいこと

| 目標 | できたと判断するための姿 |
| --- | --- |
| 実用のミニアプリを束ねられる | 複数画面や保存データを持つ、用途の異なる複数のミニアプリが共存し、日常の用途を果たす。カウンターの検証例だけでは判断しない。 |
| 追加・変更を繰り返せる | 作者以外のゆる開発者も、手順と実例からミニアプリを追加できる。通常の追加で基盤内部を大きく書き換える必要がない。 |
| データを守って運用できる | 保存形式の変更や基盤更新に移行方法があり、バックアップから戻す手段を確認できる。更新に失敗したときも復旧方法が分かる。 |
| iPhoneで継続して使える | SideStoreでの導入・署名更新、ショートカット、Widget、通知が実用のミニアプリでも動く。対応環境と、できないことが明確。 |
| 公開基盤を更新し続けられる | 公開側の改善を自分用の派生へ取り込み、必要な修正箇所が分かる。ミニアプリが依存してよい部分と、変更時の移行方針が明確。 |

「不具合が一切ない」「今後の更新で一切修正不要」を1.0の意味にしない。どこを安定させ、変更時に何を守るかを明確にする。

## 0.1との関係

0.1は、[確定済みのF1〜F7・O1〜O4](2026-08-28-jibunkit-foundation-design.md)をすべて満たす基盤を届ける版。ショートカット、Widget、通知、更新時の保存維持、GitHub公開と運用文書はすでに0.1に含まれる。

1.0では、それらを実用のミニアプリと継続利用で確かめ、追加開発・更新・復旧の手順を安定させる方向を提案する。バックアップ・復元など、0.1に含まれていない内容は新たな目標案として区別する。個別アプリの選定・移植は0.1の後に別途扱い、ここでは対象アプリを決めない。

1.0の目標を理由に、0.1の未達項目を移さない。0.1を継続して育てる原則は、0.1の範囲を拡張したり、先送りしたりする理由ではない。1.0の途中段階の番号や期限も今は増やさない。

## 将来の検討候補：IPA向けアダプタ・変換器

ユーザーから、既存IPAとこのスーパーアプリをつなぐアダプタ・変換器のような仕組みがあってもよい、という候補が挙がっている。時期は1.0に限定せず、その後でもよい。

**扱いは将来検討（DEFERRED）。0.1にも1.0にも必須化しない。** 現時点では実現方式、対応するIPAの条件、ソースコードの必要性、機能の保持範囲、利用・配布条件を調査していない。汎用的な自動変換が可能だとは約束しない。

この候補に備えた抽象化やアダプタの空実装は作らない。具体的な対象と需要が決まった時点で、既存基盤を活かせる方法と制約を調査する。採用時に現在の方式と両立しない点が判明したら、その影響を説明して判断し、0.1の単純破棄を既定路線にしない。

## 自動的には含めないもの

ミニアプリのストア、ビルド不要の追加、任意の既存IPAの実行、クラウド同期、あらゆる既存アプリの無修正移植、全機種・全OSの保証は、この目標案からは導かない。IPA向けアダプタ・変換器を検討候補に残すことと、任意のIPAの実行を保証することは区別する。Widgetからの操作やアプリを開かないショートカット実行も、自動的に1.0の必須機能へ繰り上げない。

## 今決める範囲

今は0.1からの継続性とYAGNIの原則を固定し、到達像の細目は広げない。1.0へ向けた開発を始める前に、実用ミニアプリの種類、対応環境、安定させる範囲、復元の対象を観察可能な完成条件にする。技術方式は、その条件を実現する手段として選ぶ。
