# スーパーアプリ基盤 1.0の目標案と設計原則

更新日: 2026-09-07

**状態: 0.1からの継続性を維持し、2026-09-07の合意により共通基盤の先行設計・実装を認める原則を試行する。以下の到達像は目標案であり、個別機能・完成基準・期限を一括承認されたものではない。ソースコードがある独立Swift／SwiftUIアプリのFeature化支援は1.0の目標候補。0.1の必須条件は変更しない。**

## 確定した設計原則

**0.1を1.0へ育てていく。1.0で別路線へ進み、単純に破棄することが分かっている0.1専用の仕様は作らない。ミニアプリの追加・変更・継続利用を容易にする基盤を、プロダクトの主要な成果物として扱う。**

- 0.1で作るスーパーアプリ本体、ミニアプリの追加方法、保存データの扱い、検証・運用文書を、その後も育てる前提にする。カウンターのサンプルだけを成立させるために、本体をカウンター専用にしない。
- 個別ミニアプリの実装や既存サンプルを前提とせず、目指す開発体験と運用上の要求から共通機構を先行設計・実装してよい。
- 設計の妥当性は、実装・利用・検証を通じて継続的に見直す。具体例やサンプルは検証・改善の手段であり、着手の前提条件にはしない。
- 汎用化の範囲は、目的への効果と複雑さ・保守負担から判断する。既存の使用例がないことだけを不採用の理由にしない。
- 基盤はミニアプリの組込み境界と共通APIの正しさを担保する。Feature固有の不具合を吸収して正常に見せることは目的にせず、入力・データ形式・業務処理の正しさはFeature側の責任として扱う。
- 現時点で分かっている1.0の方向性との矛盾は、0.1の設計時に避ける。未知の要件を予測してすべて吸収する設計は求めない。
- 継続性は「すべてのコード・内部構成を永久に維持する」という意味ではない。実装・利用で判明した問題に対する変更は認めるが、理由、利用者への影響、既存ミニアプリとデータの移行方法を示す。将来の版だからという理由だけで全体を破棄しない。
- 成立性を調べるためだけの一時的な検証物は、継続して使う製品実装と区別する。検証物を作ったことを0.1の製品完成に数えない。

## 目指す状態

### 想定する利用者とFeatureの規模

有料Developer Programへの加入を決めるほどの自信作ができる前から、複数の自作アプリを作り込み、日常利用したい人のための開発環境を目指す。SideStoreのアプリ枠やLiveContainerの制約に満足しないという利用動機を踏まえ、JibunKit自身の強い機能制限で価値を失わないことを重視する。これは、それらの環境やAppleの制約をすべて解消できるという保証ではない。

「ミニアプリ」は組込み単位であり、少ない画面数・コード量・単純な機能を要求する意味ではない。複数画面、独自のデータモデル、検索・集計、履歴、通知、バックアップなどを持ち、単独でも日常利用できる規模を想定する。追加の容易さに加え、作り込んでも行き詰まらないことを基盤の評価軸とする。現状でその全範囲を検証済みとは扱わない。

- Feature内部の構成・保存方式・依存ライブラリは、共存やビルドの条件に反しない限り選択できるようにする。現在のUserDefaults利用例を唯一の保存方式に固定しない。
- 共通化は組込みと共存に必要な接続部分を中心に行い、基盤の都合だけでFeatureの機能を削らせない。
- 制限を設ける場合は、Apple・OS・署名環境に由来する条件と、JibunKitの未対応・設計上の制限を分けて説明する。後者は改善対象として評価する。
- 個別の権限、extension、バックグラウンド処理などは必要条件を確認して対応を判断し、無条件の対応保証にも一律の対象外にも置き換えない。

### 継続利用の到達像

**ゆる開発者が、自分に必要なミニアプリを追加し、日常で使い、データを守りながらスーパーアプリと基盤を更新し続けられる。**

基盤の内部を毎回調べ直したり、作者へ都度相談したりしなくても、説明と実例を頼りに開発・運用を進められることを目指す。開発ではコード編集とビルドを行う前提を維持し、画面操作だけで何でも作れることは約束しない。

## 1.0に向けて確かめたいこと

| 目標 | できたと判断するための姿 |
| --- | --- |
| 実用のミニアプリを束ねられる | 複数画面や保存データを持つ、用途の異なる複数のミニアプリが共存し、日常の用途を果たす。カウンターの検証例だけでは判断しない。 |
| 追加・変更を繰り返せる | 作者以外のゆる開発者も、手順と実例からミニアプリを追加できる。通常の追加で基盤内部を大きく書き換える必要がない。 |
| 独立アプリをFeature化できる | ソースコードがある独立Swift／SwiftUIアプリについて、App target固有部分と再利用可能部分を見分け、Featureライブラリと薄いAdapterへ分離してJibunKitへ組み込める。必要な手作業と保持できない機能が分かる。 |
| データを守って運用できる | 保存形式の変更や基盤更新に移行方法があり、バックアップから戻す手段を確認できる。更新に失敗したときも復旧方法が分かる。 |
| iPhoneで継続して使える | SideStoreでの導入・署名更新、ショートカット、Widget、通知が実用のミニアプリでも動く。対応環境と、できないことが明確。 |
| 公開基盤を更新し続けられる | 公開側の改善を自分用の派生へ取り込み、必要な修正箇所が分かる。ミニアプリが依存してよい部分と、変更時の移行方針が明確。 |

「不具合が一切ない」「今後の更新で一切修正不要」を1.0の意味にしない。どこを安定させ、変更時に何を守るかを明確にする。

## 0.1との関係

0.1は、[確定済みのF1〜F7・O1〜O4](2026-08-28-jibunkit-foundation-design.md)をすべて満たす基盤を届ける版。ショートカット、Widget、通知、更新時の保存維持、GitHub公開と運用文書はすでに0.1に含まれる。

1.0では、それらを実用のミニアプリと継続利用で確かめ、追加開発・更新・復旧の手順を安定させる方向を提案する。バックアップ・復元など、0.1に含まれていない内容は新たな目標案として区別する。個別アプリの選定・移植は0.1の後に別途扱い、ここでは対象アプリを決めない。

1.0の目標を理由に、0.1の未達項目を移さない。0.1を継続して育てる原則は、0.1の範囲を拡張したり、先送りしたりする理由ではない。1.0の途中段階の番号や期限も今は増やさない。

## 1.0の目標候補：独立SwiftアプリのFeature化支援

ソースコードがある独立Swift／SwiftUIアプリを、JibunKitへ組み込めるFeatureライブラリと薄いAdapterへ分離する作業を支援する。単独版を維持する場合は、`@main`などのApp target固有部分をApp Shellへ残し、同じFeatureを単独版とJibunKit版から利用できる構成を目指す。

支援対象は、App entry point、Root Viewと状態生成、保存、通知、URL、entitlements、Widgetなど、独立App targetとFeatureライブラリの境界を見つけて分離する作業である。すべてのアプリを無修正で自動変換することは目標にしない。支援を文書、診断、雛形生成、コード変換のどこまで行うかと、1.0の完成条件は、代表的なアプリ構成を確認してから決める。

2026-09-04のJibunKitは、Featureを受け取る`MiniAppDescriptor`と`MiniAppContext`までを実装している。独立アプリを解析・分離する支援機能は、この時点では実装していない。今後その支援を追加する場合も、現在のRegistryとFeature境界を活かし、0.1の単純破棄を既定路線にしない。

## 自動的には含めないもの

ミニアプリのストア、ビルド不要の追加、コンパイル済みアプリの動的実行、クラウド同期、あらゆる既存アプリの無修正移植、全機種・全OSの保証は、この目標案からは導かない。Feature化支援は、ソースコードを基に必要な分離と変更を行う前提である。Widgetからの操作やアプリを開かないショートカット実行も、自動的に1.0の必須機能へ繰り上げない。

## 今決める範囲

2026-09-07からは、0.1からの継続性と独立アプリのFeature化支援という方向を保ち、共通基盤の先行設計・実装を認める原則を試行する。この変更だけで個別機能を1.0の必須条件にはしない。1.0の完成条件を決める際に、実用ミニアプリの種類、Feature化支援の範囲、対応環境、安定させる範囲、復元の対象を観察可能な条件にする。技術方式は、その条件を実現する手段として選ぶ。

## 設計原則の変更履歴

- 2026-09-07: 「今必要でないものは作らない」という一律の先行実装制限を弱め、基盤そのものの製品価値から着手を判断する方針を試行する。個別アプリやサンプルの先行完成を要求しない。0.1の完成条件、保存データの継続性、個別機能の承認範囲は維持する。
