# Swift Package resource and localization comparison (2026-09-11)

## Question

When two Swift packages contain the same resource filename and localization key but different values, does standard `Bundle.module` preserve each package's values when built alone and together? After removing Feature A and regenerating into the same DerivedData, does Feature B still read its own values, independently of any stale A bundle left on disk?

## Fixture and boundaries

`Tests/PackageResources/FeatureA` and `FeatureB` are independent Swift packages. Each processes a resource named `shared.json` and `en.lproj` / `ja.lproj` `Localizable.strings` files containing the key `shared.greeting`. A's values identify A and B's identify B. Their public readers use only `Bundle.module`, `JSONSerialization`, and standard `Bundle` lookup. The dedicated host declares `CFBundleLocalizations = [en, ja]`, English as its development region, and `CFBundleAllowMixedLocalizations = true`; Apple defines the latter as allowing localized-string retrieval from framework bundles. Each configuration is launched separately with English and Japanese app-language settings and verifies ordinary `Bundle.module.localizedString`. Explicit en/ja sub-bundle reads are retained as a separate resource-presence comparison, not as evidence of normal language selection.

The optional `package_resources_validation` CI hook generates a dedicated iOS app and UI test. With one app identity and one DerivedData directory it executes A-only, B-only, combined A+B, then B-only after regenerating the project without A. Every run reads actual JSON and explicit English/Japanese localized values in the simulator. After the combined build and after the removal build, the hook separately counts any A resource bundles still present in DerivedData; runtime correctness is not inferred from filesystem cleanup.

This comparison covers SwiftPM resource-bundle identity, the standard package accessor, explicit en/ja lookup, generated-project dependency removal, and this build cache sequence. It does not establish coexistence for arbitrary SDK globals or runtime singletons. No custom resource generator or cleanup step is introduced.

Run [34569632534](https://github.com/y-aplus/JibunKit/actions/runs/34569632534) established the explicit resource-presence baseline. A-only returned `A|Hello from A|Aからこんにちは`; B-only returned the corresponding B values; combined returned both complete A then B value sets; and B after A removal still returned only B's values. Two A resource-bundle directories existed in DerivedData before removal and one remained afterward, while the regenerated/rerun app still read B correctly. Thus stale on-disk A output and runtime B lookup are distinct. This run predates the host localization declaration and does not establish ordinary preferred-language selection.

Run [34570995724](https://github.com/y-aplus/JibunKit/actions/runs/34570995724) is the successful source for the corrected host-language comparison at commit `009f713`. Each result is ordered as JSON owner, ordinary preferred-language lookup, explicit English lookup, and explicit Japanese lookup:

- A-only (19.288 seconds): English returned `A|Hello from A|Hello from A|Aからこんにちは`; Japanese returned `A|Aからこんにちは|Hello from A|Aからこんにちは`.
- B-only (18.727 seconds): English returned `B|Hello from B|Hello from B|Bからこんにちは`; Japanese returned `B|Bからこんにちは|Hello from B|Bからこんにちは`.
- Combined A+B (22.396 seconds): English returned `A|Hello from A|Hello from A|Aからこんにちは|B|Hello from B|Hello from B|Bからこんにちは`; Japanese returned `A|Aからこんにちは|Hello from A|Aからこんにちは|B|Bからこんにちは|Hello from B|Bからこんにちは`.
- B-only after removing A and regenerating into the same DerivedData (14.092 seconds): English and Japanese repeated the exact B-only values above.

There were two A resource-bundle directories in DerivedData after the combined build and one after the regenerated B-only build. The remaining stale A directory is an on-disk cache observation; it did not cause B to load A's JSON or localized string at runtime. The existing mini-app Search regression also passed in 37.953 seconds.

The host localization declaration is part of the verified standard connection, not optional test decoration: without it, earlier runs fell back to English during a Japanese launch. The app-side fixture now exposes the observed preferred language separately, and its UI test requires that value to equal the requested en/ja language before accepting the resource result. This closes the earlier assertion weakness where an ignored `-AppleLanguages` request and an English fallback could agree with each other.

## Real generated-host connection (verified and integrated)

The production app and Widget extension set `CFBundleAllowMixedLocalizations = true` in their base Info.plists while retaining the existing generated English/Japanese `CFBundleDisplayName` strings. This is a host setting only: package strings remain in their SwiftPM resource bundles and are still read through ordinary `Bundle.module` APIs. The existing build-requirement composer accepts a Feature requesting the identical boolean but rejects a conflicting value instead of silently replacing either the host or Feature request.

When `feature_validation`, `simulator_tests`, and `package_resources_validation` are enabled together, CI copies both resource fixtures into the temporary generated JibunKit host, adds them as package products, and adds a CI-only mini-app probe and UI test. These files are not dependencies or sources of the production project and therefore are not shipped in its IPA. The generated host test checks A and B simultaneously for English and Japanese, plus French: French exists in both package bundles but the host intentionally has no French `InfoPlist.strings`. For every case it first asserts requested language equals the language observed in the app, then compares exact JSON ownership and ordinary localized values from both packages.

The production artifact check separately reads `CFBundleAllowMixedLocalizations` from both the built app Info.plist and the built Widget extension Info.plist. That assertion covers Widget configuration only; it is not presented as Widget rendering or timeline-localization evidence and does not alter the independent package Widget gallery lane.

Run [34573512201](https://github.com/y-aplus/JibunKit/actions/runs/34573512201) used source `909c38c`. Native build-requirement validation passed, as did the generated-host Release build and the production artifact checks showing `CFBundleAllowMixedLocalizations = true` in both the app and Widget Info.plists. All four dedicated resource configurations passed with requested language equal to observed language; the same stale-bundle counts remained two before removal and one afterward. The generated JibunKit host returned exact ordinary values for both packages in English (`A|Hello from A|B|Hello from B`), Japanese (`A|Aからこんにちは|B|Bからこんにちは`), and host-absent French (`A|Bonjour de A|B|Bonjour de B`); its selected UI test passed in 28.346 seconds.

The overall run failed in the separately selected generated-Feature navigation regression before the normal Search check ran. Adding the CI-only package probe near the front exposed the test's assumption that the long lazy launcher initially materializes Notes/Counter/Reminder. The fixture injection now appends the package probe after the existing host entries, preserving their order and positions. The test helper also searches in both directions with bounded scrolling before requiring a row to exist, and reads its frame only after existence is established. Merely moving the probe would not have removed that fragile test assumption. At that point a focused confirmation of the integration adjustment and Search remained pending; none of the observed package-localization values had failed.

Run [34576630151](https://github.com/y-aplus/JibunKit/actions/runs/34576630151) confirmed the complete correction at source `5863cac`. Native requirement composition, generated-host Release build, production build/IPA, and separate app/Widget mixed-localization Info.plist checks passed. The four dedicated resource configurations again passed with requested language equal to observed language and exact A/B values; stale A bundle counts remained two before removal and one afterward. In the generated JibunKit host, the ordinary A/B results were exact for observed English, Japanese, and French, and the selected language method passed in 26.408 seconds. The bounded lazy-list traversal preserved the existing generated Feature navigation test, which passed in 84.945 seconds, and the separately selected Search regression passed in 42.278 seconds. This verifies the scoped host/package localization contract; it does not add evidence for Widget rendering or arbitrary SDK/global-state coexistence.
