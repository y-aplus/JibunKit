## 実装した範囲

- `check-feature-connection.py`は標準の`swift package dump-package`と`tuist dump`を呼び、ローカルPackageのpath、library product、所属target、指定hostの直接product依存を診断。Swiftソースを正規表現で推定しない。推移的Integration依存やコンパイル、Registry登録の保証はしない。
- Tuist 4.207.0の[Package](https://github.com/tuist/tuist/blob/4.207.0/cli/Sources/ProjectDescription/Package.swift)、[Path](https://github.com/tuist/tuist/blob/4.207.0/cli/Sources/ProjectDescription/Path.swift)、[TargetDependency](https://github.com/tuist/tuist/blob/4.207.0/cli/Sources/ProjectDescription/TargetDependency.swift)のCodable形を根拠にし、未知の形は診断不能として失敗にする。現在のPython試験データは手作りで、実Tuist出力の試験はまだ残る。
- `verify-feature-connection.py`で小さいnative manifestを作り、正常→path欠落/product誤名/target欠落/host依存欠落を別々に評価→修正後正常の操作列を用意した。既存CI stepへまとめて接続し、失敗例ごとにrunを作らない。
- `MiniAppValidator.validate(ids:expectedIDs:)`で実際のRegistryに必要なIDがあるかを診断。期待集合外のFeatureは許容し、従来の重複診断を維持する。P0COnboardingProbe/UITestsは生成hostの実Registryを検査してNotesの通常URLへ進む。
- 文書担当は2文書の一括提出`11f556e`。親がレビューし、診断コマンドとRegistryの確認範囲を追記した。個別CIは0。薄いIntegration、P0-Aの寿命/保存接続、P0-Bの今後の管理接続、二Packageの片側互換更新と復旧を手順へ記載した。
