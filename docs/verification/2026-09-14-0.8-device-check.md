## 1. ShortcutsとWidget

### 1a. 保存したShortcutsの実行

アプリの「Intent診断A/B」で候補名を別々に保存する。OSのショートカットでJibunKitの`Add Feature A value`/`Add Feature B value`（短い表示は`Add A/B`）を見つけ、Amountを指定する。結果の数値を表示するアクションにつなぎ、このworkflowを保存して実行する。Aは例として+2、その後-1で増減を確認し、アプリで「値と候補を再読込」した値と戻り値が一致するか確認する。A操作中にBが変化しないことも確認する。

`Read Feature A entry`/`Read Feature B entry`のEntry候補が各Featureで保存したものだけになり、選んだ名前が戻るか確認する。アプリ再起動後にも、保存したworkflowとアプリ側の値・候補が保たれることを確認する。診断画面の「1を追加」だけではOS入口の確認を代替しない。

### 1b. Shortcutsの取消・失敗と管理

Aの現在値を控える。「次の保存を5秒遅延」を押し、アプリを強制終了せずShortcutsへ切り替え、保存したA加算workflowを開始して5秒以内に停止する。Aの値を再読込し、停止前の値とBが保持されることを確認する。停止操作に間に合わなかった場合は成功とせず、その旨を記録する。

次にAで「次の保存を失敗」を押してA workflowを実行する。エラー表示と旧値保持、その次の実行では正常に加算されることを確認する。通常「管理」でIntent診断Aだけを無効化した場合は、保存済みA workflowと候補取得が拒否され、Bは使えることを確認する。Aを削除して再登録した後はAの値・候補が空、Bは保持されることを確認する。

### 1c. Widgetの表示と管理

ホーム画面にJibunKitの「機能A」「機能B」Widgetを置き、アプリの同名画面から各値を別々に増やす。表示更新後にAだけを無効化→再有効化→削除する。各段階でBの数値とWidgetを保持し、A削除後の再登録では古い値が復活しないことを確認する。アプリ再起動後にも状態と値を保持することを確認する。即時更新を前提にせず、更新しない場合は経過時間と表示を記録する。

## 2. OSの共有から受信

### 2a. 共有から保存・取込み

「受信検証A/B」の「OS共有シート」から文字列・URL・ファイルを共有し、共有先JibunKitで受信先を選ぶ。その後、本体の「受信」で対象の「取り込む / 再試行」を押す。共有完了だけではFeatureへの取込みは完了しない。選んだ側だけに内容が入り、もう一方を変えないことを確認する。一度は共有を取消し、新規取込みが増えないことも確認する。アプリを終了して開き直し、保存済みの内容を確認する。「A/Bへ受信を保存」は内部投入のため、このOS確認には使わない。

### 2b. Filesから開く

同じ「ファイルを共有」から診断用txtを「ファイルに保存」する。Files側でそのtxtをJibunKitで開き、本体の「受信先を選択」に進む場合は一度キャンセルして取込みが増えないことを確認し、開き直して対象を選択・取込みする。OSが共有先のJibunKitしか提示しない場合は2aの経路なので、本体へ直接開く経路は未確認と記録する。OSによる表示の違いを成功へ読み替えない。

### 2c. OSから受けたデータの失敗・再試行

受信検証Aの「保存後に一度失敗させる」を押す。2aまたは2bで新しいデータをAへ受信し、本体の「取り込む / 再試行」を押す。失敗後も未取込みの行が残り、再試行後に消えること、Aの件数は一件だけ増え、Bは変わらないことを確認する。保存後の応答だけを失敗させる診断であり、二重取込みを防ぐ確認になる。

## 3. 通知の操作・添付・他方保持

「通知検証A/B」で通知を許可する。Aで「5秒後に配信」を押したらホーム画面へ戻り、届いたカードを長押しして画像と「記録」「返信」を確認する。

- 「記録」後、Aの「実データを再読込」で`p1-notification-a action=mark text=none`。
- Aをもう一度配信し、「返信」で`check-A`を送信。Aで`p1-notification-a action=reply text=check-A`。Bの操作記録は変わらない。
- Bを配信し、その通知カードは操作せず残す。Aの「この所有者の通知を解除」を実行しても、通知センターのBカードが残ることを確認する。Aの管理削除後もBを保持する。
- 再登録したAとBで、アプリを開いたまま別々に配信する。Aはバナーなしで`policy=silent`、Bはバナーありで`policy=banner`。表示先が別Featureでも方針の所有先が入れ替わらないことを確認する。

集中モード等で配信を確認できなかった場合は成功とせず、操作できなかった範囲を記録する。文字列一致とOSカードの実動作を別々に確認する。

## 4. HTTP/Webと認証

- HTTPのA/Bを開き、それぞれ`Login and persist`。A/B別のCookie/認証値が出ることを確認し、その起動中に`Read owner cache`で各所有者の応答を確認する。アプリ再起動後は`Reload persisted HTTP state`でCookie/認証を確認する。URLCacheはOSによる破棄があり、再起動・上書き・署名更新をまたぐ永続性の必須条件にはしない。これは仮の診断資格情報で、実アカウントの入力は不要。
- Aで`Hold writer`→`Cancel held writer`。`cancelled held-write; no late cookie`となり、元のCookieを保持することを確認する。
- WebのA/Bで「保存」。再起動後に「読込」し、local/cookie/indexeddbがそのownerのままであることを確認する。
- WebのA/Bで「認証開始」し、OSページの`Return to App`を押す。各々`completed p1-web-a/b`。Bの「認証取消検証」でOSの閉じる操作を行い、Bが`cancelled`、Aの結果は保持されることを確認する。

## 5. 上書き・署名更新と片側logout

4のA/Bデータを保持したまま同じ診断IPAをSideStoreで上書きし、HTTP/Webの読込とWidget/受信の保存値を確認する。SideStoreの署名更新も行い、同じ確認をする。上書きと署名更新を行えた範囲を区別して記録する。

HTTP Aで`Stop writers, then logout`→画面を開き直す→`Reload persisted HTTP state`。Aが空Cookie/`unauthenticated`となり、Bは保持されることを確認する。Web Aだけを管理から削除し、Bの保存値を保持することを確認する。

最後に案内する通常IPAへ上書きし、Counter/Reminderと既存の通常Widget/Shortcutを確認する。診断Featureが一覧からなくなることは候補だけの構成による。これまでの0.7実機確認を、新しいP1の成功として転記しない。
